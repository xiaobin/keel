# 0008. 非需求入口载体：统一走普通 change，不加新机制

- 状态：已决定（2026-10-23）
- 关联：0002 §8 未决问题 1；0002 §6.3 缺口 G2（archive 无扩展 scope）

## 背景

atlas 入口矩阵除了需求级主路径（apply <需求ID>），还有治理补账、backfill 回流、无卡修订、
事实刷新（after_finish hook）、纪元退役等非需求入口。0002 把「这些入口在 keel 的载体」
列为未决：独立 Standalone 应用 vs Native 修订通道。

## 决定

**统一载体 = 普通 keel change，不建新机制。** 逐入口对账：

| atlas 入口 | keel 载体 | 理由 |
| --- | --- | --- |
| 治理补账（补欠账资产） | 普通 change（brief 写明补账范围） | 补账=改 `product/**` 资产，governance-suite/closeout 天然按改后状态裁决，无需特殊通道 |
| backfill 回流 | 普通 change | 同上：回流是资产编辑，门禁不关心动机 |
| 无卡修订 | 普通 change | 门禁不区分变更大小；嫌重的是流程不是载体，轻量化的正确位置是 brief/验收写法 |
| 纪元退役（三件套） | 普通 change（退役 brief + 验收写退役判据） | 退役产物仍落 `product/**` 与归档区，走同一生命周期可审计 |
| 事实刷新（after_finish） | **例外，暂缓**：受 G2 阻挡（archive 阶段无扩展 scope，机器门挂不上）；interim 由操作者在 archive 后手动跑结构环刷新并提交，或后续加 `keel refresh` 动词 | keel 首靶是 greenfield（结构环零域无实然可刷）；adopt 类项目接入前必须解决，届时随 G2 一起议 |

## 依据

1. keel 生命周期（shape→build→verify→archive）与门禁链对「变更内容」无关——任何以
   `product/**` 与代码为产出的工作都能被同一套门禁裁决。入口差异在 atlas 独立模式里
   需要不同命令，是因为那里没有统一工作流；keel 有。
2. 新载体（Standalone 应用）要维护第二套 start-request/门禁装配，与 0001「治理层下沉为
   Native 工作流资产」的路线相悖。
3. 实证：selftest 的 change 从开户到归档全程无「需求」语义，门禁链照样成立——载体与
   需求无关已被验证。

## 边界

- 事实刷新是唯一被推迟的入口，阻塞于 G2；解决 G2 时一并定案（archive 扩展 scope vs
  `keel refresh` 动词）。
- brief 的「类型」字段（需求/补账/退役…）当前不入机器契约，只是叙事；若未来要按类型
  调整门禁严格度，再开 ADR。
