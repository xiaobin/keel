# Keel 安装使用手册

> 对应实现：bin/keel.mjs · scripts/onboard.mjs · application/（治理扩展族）
> 决策依据：docs/decisions/0001–0009。本文只写操作，不重复设计论证。

## 1. 前置依赖

| 依赖 | 要求 | 说明 |
| --- | --- | --- |
| Node | ≥ 22.16 | keel/comet 运行时 |
| python3 | 可用 | atlas 机器校验器（治理门本体） |
| git | 可用 | 被治理项目必须是 git 仓库 |
| comet 检出 | 默认 `../comet`，`COMET_BIN` 覆盖 | **须已构建**（`bin/comet.js` 存在）。仅作 keel 内部运行时，**你永远不需要直接运行 comet 命令** |
| atlas 检出 | 默认 `../atlas`，`KEEL_ATLAS_ROOT` 或 `keel onboard --atlas-root` 覆盖 | 开户时经其 `install.sh` 把校验器装配进你的项目 |

## 2. 安装 keel

```bash
cd keel
npm install        # 依赖为 file:../comet
npm link           # 可选：keel 命令全局可用；不 link 则用 node bin/keel.mjs
npm run selftest   # 可选：全链自验（约 5 分钟，PASS 即环境就绪）
```

`application/application.json` 仓库已带。**改动 `application/**` 后必须重建**：

```bash
npm run build:application
```

（comet 按全量内容摘要校验应用包，漂移即拒；Skill 审查证据的摘录须逐字出现在各 SKILL.md 内。）

## 3. 项目接入（每个被治理项目一次）

```bash
cd <你的项目>
git init                # 若还不是 git 仓库
```

然后开户第一个 change（change = 一次需求/治理变更的工作单元，名字须 `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`）：

```bash
keel onboard <change>
```

开户做的事（幂等，不覆盖已有资产）：

1. 装配三环资产骨架 `product/stack-profile.yaml`（按项目实况改 `origin`/`apps`）；
2. 经 atlas `install.sh --no-patch --no-wiring --force` 把校验器装进项目 `.atlas/`；
3. 候选指纹卫生：`.gitignore` 补 `__pycache__/`、`*.pyc`、`.atlas/runs/`、`.worktrees/`，已入库的 pyc 移出索引，并 burn-in 首跑让 `.trellis/spec/` 骨架落位；
4. 缺 `.comet/config.yaml` 时自动生成 Native 默认配置（`assets/comet/config.yaml`，可手改）——无需 comet init；
5. 写 `docs/comet/changes/<change>/brief.md` 骨架与 `start-request.json`；
6. 跑 `validate_stack_profile` 门（FAIL 则开户失败）。

**开户后把产物提交**（净态门要求，见 §6）。brief 须补写 Outcome/Scope/Non-goals/Acceptance 章节（骨架有引导）。

## 4. 一个 change 的生命周期

```bash
keel start <change>     # 启动 Run（前置：工作区净态，见 §6）
keel confirm <change> --summary '确认说明'   # 确认 Shape 定稿
keel build <change> --summary '交接说明'     # Builder 交接（自动采集模式，见 §5）
keel next <change>      # Runtime 自行推进：verify.checks + 四个治理扩展，全绿则停等 Verifier
keel verify <change> --payload verdict.json  # 独立 Verifier 裁决（须非 Builder 身份）
keel confirm <change> --summary '验收说明'   # 用户验收（含 verify.revalidate 复核）
keel next <change>      # 推进 archive.prepare/execute/finalize
keel archive <change>   # 完成归档
```

随时 `keel status <change>` 看阶段与待办；`keel next` 在需要人操作时给出提示。

各阶段的治理门（Native 扩展，fail 自动打回 Builder 修复轮，修复轮同样用 `keel build` 交接）：

| 链位顺序 | 扩展 | 判据 |
| --- | --- | --- |
| verify.checks 之后 1 | governance-suite | `atlas_check --fast` 无 FAIL（SKIP 全量进摘要） |
| 2 | independent-review | `product/reviews/review.json` + README 存在且形态合规（Critical/对账不过 ⇒ fail） |
| 3 | closeout | `atlas_check` 全量（含出厂测试与 E2E 真跑，~23s）无 FAIL |
| 4 | walkthrough-gates | 走查留痕齐备（见 §5.3；零域项目 NA） |
| 之后 | verify.verifier | comet 原生独立 Verifier，语义裁决 |

Supervisor 多子任务流：`keel confirm --coordination-mode multi-session`，children 契约见 `docs/decisions/0009`。

## 5. 资产与交付契约

### 5.1 Builder 交接（`keel build`）

- `--summary` 自动采集模式（推荐）：验收 ID 读 Run 状态，证据 = `docs/comet/changes/<change>/` 现存文件（排除运行时文件），自动生成 verificationChecks（文件存在性 + PRD 门）。
- `--payload <f.json>` 手工模式，字段：`{summary, acceptanceReview:[{id,status:'implemented-with-evidence',evidence:[...],note}], checks:[{name,result:'passed|failed|not-run',note}], knownLimits, verificationChecks}`。`evidence` 每条非空。

### 5.2 Verifier 裁决（`keel verify`）

`--payload <f.json>`：`{verdict:'pass|fail|revise-requirements', summary, acceptance:[{id,result:'passed|failed',reason}], risks}`。payload 文件**必须放项目外**（否则污染候选指纹）。缺省时自动从 verify.checks 结果采集 evidence.checks。

### 5.3 应然资产（治理门检查对象）

| 资产 | 位置 | 门 |
| --- | --- | --- |
| stack-profile | `product/stack-profile.yaml` | 开户门 + 各扩展 artifactRefs |
| PRD | `product/prd/prd.md`（Shape 阶段撰写，greenfield 此前治理门红属预期） | validate_prd |
| 实例⑤审查报告 | `product/reviews/review.json` + `README.md`（每 change 覆盖，历史走 git） | independent-review |
| 走查单确认 | PRD「用户旅程走查」节内 `已确认：<YYYY-MM-DD>` 行 | walkthrough-gates（有用例时） |
| 验收走查留痕 | `product/e2e/reviews/<日期>-acceptance-<域>/README.md`，含「手工项：N 项」评估行与「验收走查：通过」 | walkthrough-gates（有用例时） |

## 6. 铁律与故障排查

1. **物理路径**：`--project-root` 必须等于 `realpath`（软链路径直接拒绝）。macOS 的 `/tmp` 是 `/private/tmp` 软链——试验场放 `$HOME` 下或用 `realpath`。（0005 §2 S1）
2. **净态门**：`keel start` 时 `git status --porcelain` 非空即拒（排除运行时文件）。Run 中途任何被跟踪文件变化 = 候选门漂移，会把 verify.revalidate 锁死（**无向前恢复出口**，0009）——开工前提交干净，Run 期间勿手改。
3. **调度请求文件一律项目外**：keel CLI 已内化（写 `os.tmpdir()`），手工 comet 操作时同样遵守。
4. **用仓内 comet**：keel 默认找 `../comet/bin/comet.js`，`COMET_BIN` 覆盖；PATH 全局 comet 版本不符会缺命令。
5. 报错 `INVALID_WORKFLOW: Skill 审查证据与真实文件不匹配` ⇒ `application/**` 改后没跑 `npm run build:application`。
6. `OUTCOME_REJECTED`/`OUTCOME_CONFLICT` ⇒ 被拒 outcome 也占位，payload 修正后换 outcomeId 重交（keel CLI 自动处理）。

## 7. 环境变量速查

| 变量 | 默认 | 用途 |
| --- | --- | --- |
| `COMET_BIN` | `../comet/bin/comet.js` | comet CLI 路径 |
| `COMET_VERSION` | 读 `../comet/package.json` | 重建 application.json 时的 runtimeVersion |
| `KEEL_ATLAS_ROOT` | `../atlas` | atlas 检出位置（开户装配备与治理门脚本解析） |

## 8. 自验

```bash
npm run selftest
```

在临时目录从零建项目，走完全链到 `archive/done`（含四个治理扩展真跑），约 5 分钟。失败保留试验场路径供排查。
